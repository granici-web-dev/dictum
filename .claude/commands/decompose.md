Прочитай `outputs/prd.md`. Работай с таблицей «Скоп MVP»: строки с `ID`, приоритетом, зависимостями и критерием готовности.

## Алгоритм

1. Возьми только строки Must и Should. Could и Won't — в отдельный список «Отложено», без разбивки.
2. Сгруппируй строки в **фазы** по зависимостям: фаза N содержит только то, чьи зависимости закрыты фазами < N. Первая фаза — всегда «сквозной сценарий»: минимум, при котором главный сценарий из PRD проходит от начала до конца.
3. Каждую строку разбей на **issues**. Хороший бэклог этого прогона — доска, которую человек охватывает взглядом: **8-12 задач на весь прогон**, каждая размером в самостоятельный кусок работы. Больше двенадцати означает, что бэклог нарезан мельче, чем по нему работают: карточка на пятнадцать минут стоит дороже в чтении и перетаскивании, чем в исполнении. Правила размера и формы:
   - один issue — самостоятельный кусок работы, обычно от половины дня и не больше одного рабочего дня для одного человека; больше — режь дальше;
   - задача меньше двух часов (`estimate: S`) — повод поискать, с чем её объединить, а не завести отдельную карточку; такие остаются редким исключением, а не половиной доски;
   - у каждого issue есть `title`, `description` (1-2 предложения: что и зачем), `dod` (Definition of Done — ровно 2 проверяемых пункта, самых важных), `depends_on` (ID других issues), `phase`, `scope_id` (ID строки PRD), `area` (frontend / backend / design / infra / research), `estimate`, `test_hint`;
   - `title` — глагол и объект, не длиннее восьми слов и 100 символов, без придаточных: «Отправлять сводку в командный чат», а не «Реализовать механизм, который отправляет сводку в чат, если у карточек истёк срок». Длинный заголовок обычно значит, что issue не дорезан, а условия из него — это `dod`;
   - `estimate` — `S` (меньше 2 часов), `M` (до половины дня), `L` (до дня). Больше дня не бывает: такую задачу режь дальше;
   - `test_hint` — одна конкретная строка о том, как проверить готовность: команда, сценарий или файл. Не «протестировать функциональность», а «`pytest tests/test_trello.py::test_due_filter`» или «в чате в 9:00 приходит сводка с тремя карточками»;
   - не создавай issues вида «сделать бэкенд» или «настроить проект» без конкретного результата;
   - не создавай issues на то, чего нет в PRD — если чего-то не хватает для реализации, добавь в «Открытые вопросы», а не в бэклог.
4. Перечисляй issues в порядке зависимостей: каждый `depends_on` указывает на issue, который уже стоит выше в списке. Ссылка вниз означает, что порядок неверный, а не что задача особенная. При таком порядке цикл невозможно записать.
5. Проверь граф зависимостей: без циклов, каждый `depends_on` существует.
6. Сохрани `outputs/issues.json`.

## Выход

`outputs/issues.json`:

```
{
  "source": "outputs/prd.md",
  "lang": "[из brief.md]",
  "phases": [
    { "n": 1, "title": "Сквозной сценарий", "goal": "…" }
  ],
  "issues": [
    {
      "id": "I-001",
      "phase": 1,
      "scope_id": "S1",
      "area": "backend",
      "title": "…",
      "description": "…",
      "dod": ["…", "…"],
      "depends_on": [],
      "estimate": "S | M | L",
      "test_hint": "…"
    }
  ],
  "deferred": [ { "scope_id": "S7", "title": "…", "reason": "…" } ],
  "open_questions": ["…"]
}
```

## Правила

- Язык — из frontmatter брифа.
- Не выдумывай требования. Сомневаешься — в «Открытые вопросы».
- Идентификаторы стабильны при повторном прогоне: если PRD не менялся, `I-001` остаётся `I-001`.
- `title` отложенного скоупа — его название из колонки «Сценарий / экран» таблицы «Скоп MVP», слово в слово. Оно становится названием карточки в бэклоге, и `scope_id` вместо него читается как шифр.
- Объединяя мелкие задачи, объединяй и их `dod`: два пункта на карточку, а не сумма пунктов слитых. Пункт `dod` — то, что проверяют перед закрытием, а не пересказ описания.
- `reason` отложенного объясняет, почему скоуп не вошёл в MVP, а не повторяет приоритет: «Could» само по себе ничего не сообщает тому, кто откроет карточку через месяц.
- **У экрана есть дизайн.** Строка скопа, за которой стоит экран, диалог, уведомление, пустое состояние или ошибка — всё, что человек видит, — получает отдельный issue с `area: design`: макет этого места. Его `dod` — «фрейм в Figma» и «ссылка на фрейм в карточке». Задачи кода по тому же экрану ставят этот issue в `depends_on`: экран рисуют до того, как верстают, а не после. Один фрейм может закрывать несколько экранов сразу — тогда его ставит в `depends_on` каждая задача кода по любому из них, даже если её `scope_id` другой: тот, кто возьмёт карточку, ищет ссылку на фрейм в ней, а не в DoD чужой задачи. Строке без интерфейса (интеграция, обработка данных, расписание, отправка) дизайн не нужен, и придумывать его там не надо.

## Последнее

Пиши **только** `outputs/issues.json`, одним блоком `<file>`. Второго файла не пиши:
`outputs/issues.md` — тот же бэклог прозой — собирает код из этого JSON и показывает человеку
на воротах перед публикацией. Копия, присланная вместе с JSON, выбрасывается, а её половина
ответа оплачена: на живом прогоне это 9585 токенов, из которых половина ушла в мусор.
