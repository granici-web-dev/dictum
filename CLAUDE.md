# idea2backlog — правила проекта для Claude Code

Внутренний инструмент: идея (голосовое в Telegram, MP3-запись, текст) → бриф → ресёрч → PRD → декомпозиция → карточки в Trello. Рабочее название, переименовать можно позже.

## Как читать этот репозиторий
- `SPEC.md` — архитектура, стадии, контракты данных. Источник истины по поведению.
- `PLAN.md` — фазы и текущая задача. Всегда работай над тем, что там помечено как текущее.
- `.claude/commands/*.md` — пять промпт-стадий (`/intake /brief /research /prd /decompose`) + `/publish`. Это **движок продукта**: в коде они вызываются как системные промпты через Anthropic API. Правишь промпт — правишь продукт.
- `templates/prd_oneshot.md` — шаблон PRD. Формат таблицы «Скоп MVP» — контракт для `/decompose`.
- `inputs/`, `outputs/` — рабочие файлы одного прогона (в git не идут).
- Соглашения — в `CONVENTIONS.md` (принципы, стек, тестирование). Стек не менять без записи в `SPEC.md`.

## Правила работы
1. **Ворота — не опция.** После `brief` и после `decompose` пайплайн останавливается и ждёт кнопку в Telegram; после `intake` он ждёт выбор идеи, пока сообщением, а не кнопкой (кнопки — P3-07), и условных ворот по `confidence: low` ещё нет (`SPEC §3.2`). Режим `auto_approve` существует только для демо и включается явно флагом `AUTO_APPROVE` в `.env`; умолчание — ворота. Вторая явная поблажка — локальный прогон `make run-text`: он идёт авто-подтверждённым, потому что интерфейса решений у него нет, а ворота без него — остановка без возможности решить. Ворота ему возвращает `ARGS=--gates`, чтобы ветку можно было пройти руками.
2. **Один формат внутри.** Любой вход становится `transcript.md` с frontmatter (`source`, `duration`, `lang`). Дальше стадии не знают, откуда пришли данные.
3. **Промпты в командах, не в коде.** Модуль `app/stages.py` читает `.claude/commands/<stage>.md` и передаёт как system prompt. Не дублируй текст промптов в Python.
4. **Язык артефактов** — `lang` из frontmatter, один на прогон. Промпты на русском, выход — на языке пользователя.
5. **Ничего не выдумывать в данных.** Если стадия не может заполнить поле — `[уточнить: ...]`, не правдоподобная заглушка. Это касается и тестовых фикстур.
6. **Каждый коммит — одно решение**, сообщение отвечает «почему», не «что». Пример: `Stop after intake when the recording holds more than one idea`.
7. **Секреты только в `.env`**, файл в `.gitignore`. Никогда не клади ключи в фикстуры, логи, тесты.
8. Согласие на запись: при загрузке аудиофайла бот требует подтверждения, что участники согласны (§ 201 StGB). Флаг ляжет в `runs.consent_confirmed` — колонки пока нет, её заводит P3-02 вместе с самими файлами. Без флага файл не обрабатывается.
9. **Стенд ходит по тегу.** Бот на конференции запускается только с коммита, помеченного тегом `stand`, и метит этот коммит последняя полная репетиция — та, где сценарий показа прошёл целиком, с замером времени и отчётом в `docs/`. `main` при этом живёт своей жизнью: между репетициями стенд не двигают, потому что «зелёные тесты» и «пять прогонов подряд без сюрпризов» — разные утверждения, и второе даёт только репетиция. Задача, попавшая в `main` после тега, на стенде не показывается, пока следующая репетиция не переставит тег.
10. **Работаем в `main`.** Ревью и CI нет, ворота — зелёный `make test` и одно решение на коммит, поэтому ветка на задачу добавила бы обряд без выгоды: прошлая прожила пять задач, и имя перестало что-либо значить. Ветка заводится там, где работа может остаться незаконченной больше чем на день или потребовать отката (чужие бинарники, внешние сервисы), и сливается по закрытии задачи. До стенда `main` обязан быть запускаемым в любой момент.

## Команды
- `make up` — postgres в docker
- `make db` — миграции (`alembic upgrade head`), после `make up` и после каждого `git pull`
- `make bot` — бот в polling-режиме
- `make test` — ruff + mypy + pytest
- `make run-text TEXT="текст идеи"` — прогон пайплайна без Telegram (для отладки стадий)

## Определение готовности задачи
Тест есть и зелёный; `make test` чист; `PLAN.md` обновлён; если менялось поведение — `SPEC.md` тоже.
