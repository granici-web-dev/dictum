# Разбор архитектуры — 08.09.2026

Состояние: фаза 1 закрыта, `app/` — 1337 строк, 117 тестов. Разбор перед фазой 2, чтобы понять,
что в ней придётся ломать.

## 1. Модули и зависимости

```
config ──────────────┐  (settings + семейство ошибок конфигурации)
models ──────┐       │
             ├─ validate ─┐
             ├─ render ───┤
             │            ├─ stages ── cli
             │            │
trello ──────┴────────────┴─ publish
```

Циклов нет. Граф — слоистый DAG в четыре уровня: листья (`config`, `models`), проверки и
отрисовка, оркестраторы стадий и публикации, входные точки.

`config` импортируют десять файлов, `models` — восемь. Для листа это нормально: `config` держит
две связанные вещи — `Settings` из окружения и семейство `ConfigError`, а `models` — схему
единственного структурированного артефакта. Ни один из них ничего не импортирует.

`bot.py`, `worker.py`, `ingest.py` — заглушки в одну строку. В графе их нет, и это честно: их
место определится в фазе 2.

## 2. Куда течёт управление

Один прогон `make run-text`:

```
cli.main            разбор аргументов, язык, коды возврата
  cli.run_pipeline  порядок стадий, файлы из outputs/ на вход следующей
    stages.run_stage    промпт из .claude/commands, вызов Anthropic, разбор <file>
      validate.check_issues   только для decompose
      render.issues_markdown  только для decompose, после проверок
    cli.write_artifact  на диск
```

Публикация — отдельная входная точка, пайплайна не касается:

```
publish.main → publish.publish → trello.Trello (транспорт)
```

Слои настоящие, каждый делает свою работу ровно один раз. Стадия решает, что за файлы; вызывающий
решает, куда их класть (`SPEC §7`). Это разделение работает: воркер фазы 2 положит те же файлы в
`runs/<run_id>/` и ничего в `stages` менять не придётся.

`publish.publish()` держит четырнадцать шагов в одной функции, но каждый шаг вынесен и назван
(`ensure_lists`, `plan_cards`, `make_card`, `revisit_card`). Функция читается как сценарий, а
сценарию так и положено. Это не находка.

## 3. Где проходят линии абстракции

Хорошие, все совпадают с настоящими швами:

- **`trello.py` против `publish.py`** — транспорт против отображения. Мокается respx на границе HTTP,
  а не подменой клиента. Линия оправдала себя: живой прогон нашёл порядок списков, потому что
  двойник моделировал позиции честно.
- **Промпты как файлы** — `.claude/commands/*.md` читаются, а не дублируются в Python. Правка
  продукта не трогает код.
- **`models.py` как контракт** — единственная схема `issues.json`, её же читают валидатор,
  рендер и публикация.
- **`ALLOW_LIVE_API`** — граница между «редактирую файлы» и «трачу деньги». Без флага клиент не
  создаётся вообще.

Плохих линий нет. Ни одного Protocol с одной реализацией, ни одного «сервиса» или «менеджера».

## 4. Единственный источник истины

Здесь два расхождения, оба видны только из фазы 2.

**`run_id` существует дважды.** `SPEC §4` объявляет таблицу `runs` с `id`, который возникает в тот
момент, когда человек прислал сообщение в Telegram. `SPEC §5` объявляет `issues.json.run_id`,
который `publish` выдумывает сам (`secrets.token_hex(4)`) в момент публикации и штампует в файл.
Это два разных идентификатора одного прогона. В фазе 2 они встретятся, и маркер на доске будет
нести не тот, по которому воркер ищет прогон в базе.

Чинить это надо **до** первой публикации из воркера, а не после: `SPEC §6.1` уже фиксирует, что
маркеры старого формата publish не читает, то есть смена формата означает чистку доски.

**`publish.json` против `publish_log`.** Это расхождение уже описано: `SPEC §6` говорит, что
таблица заменит файл в фазе 2. Планово, не долг.

Остальное состояние живёт в одном месте. Истина о публикации — на доске, файл рядом объявлен кэшем
и обратно не читается. Это решение было принято сознательно и держится.

**`settings` — модульный синглтон**, который читают `trello`, `stages`, `publish`, `cli`. Тесты его
подменяют. Для внутреннего инструмента на 1300 строк это принято открыто и цены не имеет.

## 5. Модель отказа

| Зависимость | Недоступна | Медленная | Отвечает мусором |
|---|---|---|---|
| Anthropic | `max_retries=2` в SDK, дальше `StageError`, сырой ответ в `outputs/<stage>.raw.md`, код 1 | таймаут 600 с, явный | один ремонтный повтор со списком претензий, дальше отказ |
| Trello | `TrelloError` с подсказкой про `.env`; 429 повторяется всегда, 5xx — только на GET | таймаут 30 с | pydantic на каждом ответе |
| Postgres, Redis | не существуют | | |

Это сильная часть проекта. Два решения стоит назвать отдельно.

Повтор 5xx только на чтении: POST мог дойти до Trello и потерять ответ, и второй такой же создал бы
вторую карточку. Дубль на доске хуже упавшего прогона — и это правильный выбор приоритетов для
инструмента, которому команда должна доверять.

Оборванный прогон восстанавливается: `--from <стадия>` не оплачивает заново пройденное, а `publish`
дособирает карточку, которую прошлый прогон успел создать, но не успел наполнить.

Незакрытое перечислено в `SPEC §6.1` списком из пяти пунктов, включая гонку двух publish. Не
«забыли», а «знаем и пока не платим».

## 6. Одна структурная находка

**Порядок стадий не принадлежит никому.**

`stages.py` знает пять стадий:

```python
STAGES = ("intake", "brief", "research", "prd", "decompose")
```

`cli.py` знает четыре:

```python
STAGE_ORDER = ("intake", "brief", "prd", "decompose")
```

и подделывает пятую, записывая в `outputs/research.md` строку-заглушку, потому что `/prd` просит
этот файл на вход. Сам порядок закодирован третий раз — лесенкой сравнений:

```python
from_here = STAGE_ORDER.index(start)
if from_here == 0:   ... intake
if from_here <= 1:   ... brief
if from_here <= 2:   ... prd
                     ... decompose
```

Числа в лесенке — это тот же порядок, записанный ещё раз. Два потребителя уже разошлись в том,
считать ли `research` стадией.

Это не болит сегодня и заболит дважды:

- **P2-01, воркер.** Ему нужен тот же ответ на вопрос «что после чего» — но из состояния прогона в
  базе, а не из индекса в кортеже. Второй реализации порядка неоткуда взяться, кроме как копией.
- **P4-01, настоящий `/research`.** Вставить его в лесенку — значит перенумеровать все сравнения и
  не забыть убрать заглушку.

**Что делать.** Одна упорядоченная структура, описывающая стадию: имя, какой артефакт ей нужен на
вход, какие параметры она получает, есть ли после неё ворота. `cli` идёт по ней от указанной
стадии, воркер — от той, на которой стоит прогон. Лесенка исчезает, `research` становится обычной
записью со своим режимом.

Цена: полдня с тестами. Риск низкий — это перенос данных, а не поведения; текущие тесты CLI
покрывают все четыре точки входа и поймают расхождение.

Делать это стоит **перед** P2-01, а не после: иначе копию порядка придётся выкорчёвывать уже из
двух мест.

## 7. Мелкое, названное и оставленное

`validate.check_issues` принимает текст и отдаёт список строк для человека. Из-за этого каждый
вызывающий разбирает JSON второй раз (`IssuesFile.model_validate_json`). На нынешних размерах это
ничего не стоит, а разделение «проверка отдельно, разбор отдельно» держит валидатор пригодным для
показа ошибок человеку. Оставлено сознательно.

Печать списка проблем совпадает слово в слово в `validate.main` и `publish.main` — четыре строки,
второе повторение. Правило трёх: ждём третьего потребителя.

## Три сильные стороны

1. **Модель отказа продумана до того, как понадобилась.** Разная политика повторов для чтения и
   записи, идемпотентность по маркеру на доске, досборка оборванной карточки, возобновление с
   любой стадии. Обычно это дописывают после первого инцидента.
2. **Границы совпадают с настоящими швами.** Транспорт отделён от отображения, промпты от кода,
   решение о содержимом от решения о месте. Ни одной линии, проведённой «потому что так принято».
3. **Незакрытое записано, а не забыто.** `SPEC §6.1` перечисляет пять ограничений с ценой каждого.
   Это дороже в моменте и дешевле через месяц.

## Три слабые стороны

1. **Порядок стадий не принадлежит никому** — три записи, два потребителя уже разошлись. Раздел 6.
2. **Два `run_id` на один прогон** — встретятся в фазе 2, чинить надо до первой публикации из
   воркера. Раздел 4.
3. **`research` подделан заглушкой.** Работает, описано в `SPEC §7.1`, но это стадия, которой в
   пайплайне нет, а файл от неё есть. Пока `/research` не станет настоящим, каждый читающий код
   будет спотыкаться об это дважды: в `STAGES` он есть, в `STAGE_ORDER` его нет.

## Вердикт

**Система в порядке, перестройка не нужна.** Граф чистый, слои настоящие, отказы продуманы. Двух
конкурирующих проектов не предлагаю: нечего перестраивать.

Один недостающий шов — владелец порядка стадий — стоит полдня и должен встать перед P2-01. Одно
решение — какой `run_id` настоящий — не стоит ничего сегодня и дорого стоит после первой публикации
из воркера.
