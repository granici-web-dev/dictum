# SPEC — idea2backlog

Версия 0.1 · 07.09.2026 · статус: черновик для старта разработки

## 1. Что это
Внутренний инструмент команды: любой участник даёт идею или задание — голосовым в Telegram, файлом с диктофона или текстом — и оно проходит фиксированный workflow до карточек в бэклоге Trello. Человек участвует на воротах, а не переписывает документы.

Один пайплайн, три входа: **Telegram → intake → brief → research → prd → decompose → publish**.

## 2. Не-цели MVP
- Веб-интерфейс (бот — единственный UI на MVP)
- Мультипользовательская авторизация, роли
- Диаризация говорящих
- Рыночный ресёрч по умолчанию для фич (`kind: feature` → internal/skip)
- Интеграции кроме Trello

## 3. Стадии

| Стадия | Тип | Вход | Выход | Ворота после |
|---|---|---|---|---|
| ingest | код | Telegram voice/audio/text | `transcript.md` | — |
| intake | LLM `/intake` | transcript.md | `idea.md` или `candidates.md` | если candidates или confidence=low |
| brief | LLM `/brief` batch, диалог | idea.md + ответы | `brief.md` | всегда |
| research | LLM `/research` | brief.md | `research.md` | — |
| prd | LLM `/prd` | brief, research, template | `prd.md` | — |
| decompose | LLM `/decompose` | prd.md | `issues.json`, `issues.md` | всегда |
| publish | код | issues.json | карточки Trello, `publish.json` | — |

### 3.1 ingest
- Telegram voice (`.oga`) → ffmpeg → mp3 16 kHz mono.
- Audio file (mp3/m4a/wav): проверка `consent_confirmed`, иначе отказ с пояснением.
- Файлы > 24 МБ или > 20 мин: нарезка по тишине (ffmpeg `silencedetect`), куски ≤ 10 мин с перекрытием 5 с, транскрипция каждого, склейка по перекрытию.
- Text: без транскрипции, `duration: null`, `consent_confirmed` не пишется: записи нет.
- Frontmatter transcript.md: `source`, `duration`, `lang` (Whisper language detection); `consent_confirmed` — только для аудио.

### 3.2 Ворота
Сообщение в Telegram с кратким содержанием артефакта + inline-кнопки: **Дальше** / **Править** / **Стоп**. «Править» — пользователь пишет текст, он попадает как `user_edit` в следующий вызов той же стадии (стадия перезапускается с правкой). Предыдущий ответ стадии при этом обязан идти в истории вызова, тем же механизмом, что и ремонтный повтор (§7): иначе стадия соберёт артефакт заново и идентификаторы issues поедут. Проверено вручную на прогоне 07.09.2026: с ответом в истории правка вышла точечной, изменился только один заголовок. Таймаут ворот — 24 ч, после этого run → `stalled`.

`auto_approve=true` (флаг run) пропускает ворота, кроме consent. Только для демо. Стадия `brief` при этом получает `interactive: false` — тот же параметр, которым пользуется локальный прогон (§7.1).

### 3.3 brief-диалог в Telegram
`/brief` в режиме batch задаёт вопросы по одному; ответы пользователя — обычные сообщения. Стадия хранит историю в `runs.brief_dialog` (JSON). «хватит» / кнопка «Собирай» завершает.

## 4. Данные

`runs`: id, chat_id, source, lang, kind, status (`ingesting|intake|awaiting_gate|brief|research|prd|decompose|awaiting_publish|published|failed|stalled`), consent_confirmed, auto_approve, created_at, updated_at.
`artifacts`: run_id, stage, path, version, created_at — каждая перезапись стадии = новая версия, старые не удаляются.
`gates`: run_id, stage, decision (`next|edit|stop`), user_edit, decided_at.
`publish_log`: run_id, issue_id, trello_card_id, url.

Файлы прогона лежат в `runs/<run_id>/` (S3-совместимо позже), `inputs/` и `outputs/` — только для локального запуска через `make run-text`.

## 5. Контракты артефактов
- `transcript.md`, `idea.md`, `candidates.md` — см. `/intake`
- `brief.md` — frontmatter `name`, `kind`, `lang`, `open_questions` — см. `/brief`
- `prd.md` — таблица «Скоп MVP» с `ID`, приоритет, `Зависит от`, критерий готовности — см. `/prd`
- `issues.json` — схема в `/decompose`; `run_id` верхнего уровня проставляет первая публикация и дальше не меняет: он отличает карточки этого прогона от чужих на общей доске. `deferred` несёт `scope_id`, `title` (заголовок скоупа из таблицы PRD) и `reason`; дополнительно к схеме: `estimate: "S|M|L"` (S ≤ 2 ч, M ≤ полдня, L ≤ день) и `test_hint` (одна строка, как проверить) — поля взяты из практики Task Master. Инварианты, которые проверяет `app/validate.py`: фазы нумеруются с единицы, идентификаторы уникальны, каждый `phase` объявлен в `phases`, каждый `depends_on` существует, в графе нет циклов, зависимость не указывает в более позднюю фазу (иначе фаза не собирается в самостоятельный кусок работы и `/publish` не создаст под неё список)
- `publish.json` — маппинг локального идентификатора (`I-00N`, для отложенных `S<N>`) → `key`, `card_id`, `url`. Кэш: журнал целиком восстанавливается с доски по маркерам, поэтому его потеря ничего не ломает

## 6. Trello
- Одна доска на команду, `TRELLO_BOARD_ID` в .env. Ключ и токен уходят заголовком `Authorization: OAuth …`, а не в query string: URL виден прокси и попадает в тексты ошибок. По той же причине клиент не пользуется `raise_for_status`, а поднимает своё исключение со статусом, методом и путём без параметров. Публикация закрыта тем же флагом `ALLOW_LIVE_API`, что и вызовы модели: мусорные карточки на командной доске — такой же необратимый расход, как оплаченный токен.
- Списки: `Backlog`, по одному на фазу `Phase 1: <title>` … создаются при первой публикации, если нет, и каждый новый встаёт правее прежних (`pos=bottom`): без этого Trello кладёт список в начало доски, и фазы выстраиваются справа налево.
- Ключ задачи сквозной по доске: `PROJECT_KEY-N` (`PROJECT_KEY` из .env, номер без ведущих нулей). Номер выдаёт publish при создании карточки, продолжая максимальный из маркеров на доске. Локальные `I-00N` остаются внутри прогона: их выдаёт `/decompose`, и на общей доске они сталкиваются, потому что каждый прогон начинает нумерацию заново. Сквозной ключ снимает это столкновение и даёт задаче имя, которое можно назвать вслух.
- Карточка = issue: имя `[KEY-N] <title>`, description + DoD как чеклист, label по `area`, `scope_id` в description (Trello custom fields платные — не использовать).
- Зависимости: строка «Depends on: DCT-3, DCT-7» сквозными ключами в description + attachment-ссылка на карточку. Карточки создаются в порядке зависимостей, а не в порядке файла: ссылка требует, чтобы карточка-зависимость уже существовала, а в файле зависимость может стоять ниже зависящего. Цикла не будет, его исключает §5.
- Порядок карточек в списке задаётся `pos` при создании, по порядку issue в файле, а не по порядку публикации: публикуем по зависимостям, и без этого `I-010` лёг бы выше `I-006`, что читается как сбитая нумерация. Отложенные нумеруются отдельно, внутри `Backlog`. Позиции идут от единицы, а Trello раздаёт свои десятками тысяч, поэтому опубликованная пачка садится в начало списка: на доске, где `Backlog` уже не пуст, она встанет над чужими карточками. Уже созданной карточке `pos` не выставляется и не сверяется: перетащить её руками это решение человека, а publish не арбитр.
- `deferred` из `issues.json` попадает в `Backlog` отдельными карточками: имя `[KEY-N] <title>`, причина в description, label `deferred`, чеклиста нет. Номера идут из того же счётчика, что и у issues.
- Идемпотентность: последняя строка description — маркер `dictum:<KEY-N> run:<run_id> local:<I-00N|S<N>>`. Ключ отвечает на вопрос «какой номер занят», пара `run` и `local` — на вопрос «этот issue этого прогона уже опубликован»; без `run` два прогона с одинаковыми `I-001` были бы неразличимы. Перед публикацией читаются все карточки доски, включая архивные, вместе с их чеклистами и вложениями; уже опубликованное узнаётся по маркеру. Маркер ищется терпимо к отступам и CRLF и берётся последний в описании: карточку правят руками в вебе, а текст issue может процитировать чужой маркер. Истина о публикации живёт на доске; `publish.json` рядом с `issues.json` — кэш отображения, он дописывается после каждой карточки и после прогона, содержит только ключи текущего файла и не читается обратно. Таблица `publish_log` (§4) появится в фазе 2 и заменит файл.
- Карточка с маркером, у которой не хватает чеклиста DoD, его пунктов или ссылок на зависимости, дособирается: оборвавшийся прогон успевает создать карточку раньше, чем наполнить её, и без досборки она осталась бы недоделанной навсегда. Пункты сверяются по именам, недостающие дописываются в конец, поэтому после досборки их порядок может не совпадать с `issues.json`: критерии готовности не последовательность шагов, а вычислять позицию между соседями (Trello раздаёт их от 2^47) дороже, чем стоит косметика. Существующий чеклист не пересоздаётся, чтобы не терять отметки. В выводе это «уже есть, дособрана».
- Ретраи Trello (дополнение к §7, которое там не описано, потому что относится не к модели): 429 повторяется до трёх попыток с паузой из `Retry-After`, иначе 1 с с удвоением; 5xx повторяется только на GET. Каждый повтор пишет строку в лог: молчаливый повтор не отличить от его отсутствия, а знать это нужно. Повтор POST после 5xx запрещён: запрос мог дойти и потерять ответ, а вторая такая же карточка хуже упавшего прогона.
- Коды возврата `python -m app.publish`: `0` — опубликовано, `1` — `issues.json` не прошёл проверку или доска не ответила, `64` — ошибка в аргументах или файл не читается.
- Issue, у которого маркер на доске есть, а название, description, список или лейблы разошлись с `issues.json`, пропускается и помечается в выводе «уже есть, отличается». Карточка не переписывается: правка руками на доске — тоже решение человека, а publish не арбитр.

### 6.1 Известные ограничения
- **Два publish одновременно на одну доску сделают дубли.** Между чтением доски и созданием карточки есть окно, в котором второй прогон ещё не видит чужих маркеров. На MVP публикацию запускает человек из CLI, поэтому блокировки нет; она появится, когда публиковать начнёт воркер (фаза 2) и прогонов станет несколько.
- **Маркеры старого формата не читаются.** До сквозных ключей маркер был `dictum:I-001`; такие карточки publish не узнает и опубликует заново. Демо-доска по этому случаю очищена, других досок с ними нет.
- **Стёртый маркер делает карточку невидимой.** Если строку `dictum:<id>` убрать из описания руками, следующий publish сочтёт issue неопубликованным и создаст вторую карточку. Это цена решения «истина на доске»: другого признака у нас нет.
- **Позиции карточек не чинятся после публикации.** `pos` выставляется только при создании, поэтому карточка, переставленная руками, там и останется, а перетасованный `issues.json` порядок на доске не поменяет.

## 7. Вызов LLM-стадий
`app/stages.py::run_stage(stage, inputs: dict[str, str], user_edit=None, history=None, params=None) -> StageResult`
- `inputs`: путь → содержимое; пути те же, что упоминают промпты (`inputs/transcript.md`, `outputs/brief.md`, `templates/prd_oneshot.md`).
- system = `.claude/commands/<stage>.md` + `templates/api_mode.md` (режим API: файлы приложены в тегах `<file path="...">`, сохранять нельзя, итоговые файлы выводятся в таких же тегах, ничего вне тегов).
- user = `<params>` (если есть) + `<file>`-блоки входов + `<user_edit>`, если есть. `history` — предыдущие ходы диалога (brief, P2-04), вставляются перед текущим сообщением.
- `params` — параметры запуска стадии (`mode`, `lang`, `interactive`): `brief` вызывается с `mode: batch` и `interactive: false`, `research` — с `mode` по `kind` брифа. Промпты написаны для Claude Code, где стадия ведёт диалог; в режиме API диалога нет, поэтому `templates/api_mode.md` запрещает вопросы и требует помечать неясное как `[уточнить: ...]`.
- `StageResult`: `files` (путь → содержимое из `<file>`-тегов ответа), `model`, `input_tokens`, `output_tokens`, `duration_ms`.
- Набор файлов проверяется: `intake` → ровно один из `inputs/idea.md` / `outputs/candidates.md`; `decompose` → оба `outputs/issues.json` и `outputs/issues.md`; остальные стадии → ровно один свой файл. Любой другой набор — `StageError`. Файлы на диск пишет вызывающий: CLI в `outputs/`, воркер в `runs/<run_id>/` с версиями (§4).
- Модель: `ANTHROPIC_MODEL`, для `decompose` — `ANTHROPIC_MODEL_DECOMPOSE`. Обе по умолчанию `claude-sonnet-5`; смена дефолта — правка этой строки и `.env.example`. Из ответа берутся text-блоки.
- Каждый вызов логируется: stage, model, токены, длительность; run_id добавляет воркер (фаза 2).
- Ретраи: `max_retries=2` SDK Anthropic (сетевые ошибки, 408/409/429/5xx, экспоненциальный backoff). Ответ без единого `<file>`-тега или не прошедший проверку стадии (`decompose` → `check_issues`) → один ремонтный повтор: в диалог добавляется ответ модели и список претензий. Предыдущий ответ обязательно идёт в истории: без него стадия генерирует всё заново и идентификаторы перестают быть стабильными, чего требует `/decompose`. Если и второй ответ не проходит — `StageError` со списком проблем; локальный прогон сохраняет вторую попытку в `outputs/<stage>.raw.md` и возвращает `1`, файлы стадии на диск не пишутся. Не чинятся и дают `StageError` с полем `raw` (текст ответа) сразу: `stop_reason != end_turn`, чужой набор файлов, два блока на один путь. Это сорванный контракт, а не претензия к содержимому. Токены и длительность в `StageResult` суммируются по обоим вызовам. Содержимое файла нормализуется: ровно один перевод строки в конце.

### 7.1 Локальный прогон
`app/cli.py` (`make run-text TEXT="…"` или `--file путь`) собирает `inputs/transcript.md` из текста и гонит intake → brief → prd → decompose. Если у входа есть свой frontmatter, он снимается, а `lang` берётся оттуда: иначе на прогоне вышло бы два блока frontmatter и два разных языка. Приоритет языка: `--lang`, затем frontmatter входа, затем `DEFAULT_LANG`. `brief` получает `mode: batch`, `interactive: false`, `lang`. `/research` не вызывается: `outputs/research.md` пишется строкой «Ресёрч не запускался: локальный прогон через make run-text», потому что `/prd` просит этот файл на вход. Формулировку из `mode: skip` («по решению пользователя») здесь брать нельзя: никто ничего не решал, а артефакт уходит в `/prd` как данные. `--from brief|prd|decompose` начинает прогон с указанной стадии, беря входной артефакт из `outputs/` (`inputs/idea.md` для brief): повтор упавшей стадии не оплачивает заново те, что уже прошли. Нет нужного артефакта — код `64`. Живой вызов API включается флагом `ALLOW_LIVE_API=true` в `.env`: без него клиент не создаётся и в сеть не уходит ничего. Флаг ставится на осознанный прогон, а не постоянно. Коды возврата: `0` — дошёл до конца, `1` — стадия упала (сырой ответ модели сохраняется в `outputs/<stage>.raw.md`), `2` — intake вернул кандидатов и ждёт выбора человека, `64` — ошибка в аргументах запуска. Argparse по умолчанию отдаёт на такую ошибку `2`, поэтому парсер переопределён: иначе опечатка неотличима от ожидания решения.

## 8. Нефункциональное
- EU-only: API-эндпоинты Anthropic/OpenAI с EU-регионом, где доступны; хостинг Hetzner.
- Аудио удаляется после успешной транскрипции, если `KEEP_AUDIO=false` (по умолчанию).
- Лимиты: ≤ 3 параллельных run на chat_id, ≤ 60 мин аудио на run.
