# SPEC — idea2backlog

Версия 0.1 · 07.09.2026 · статус: черновик для старта разработки

## 1. Что это
Внутренний инструмент команды: любой участник даёт идею или задание — голосовым в Telegram, файлом с диктофона или текстом — и оно проходит фиксированный workflow до карточек в бэклоге Trello. Человек участвует на воротах, а не переписывает документы.

Один пайплайн, три входа: **Telegram → intake → brief → research → prd → decompose → publish**.

## 2. Не-цели MVP
- Веб-интерфейс (бот — единственный UI на MVP)
- Мультипользовательская авторизация, роли
- Диаризация говорящих
- Рыночный ресёрч по умолчанию для фич (`kind: feature` → internal/skip)
- Интеграции кроме Trello

## 3. Стадии

| Стадия | Тип | Вход | Выход | Ворота после |
|---|---|---|---|---|
| ingest | код | Telegram voice/audio/text | `transcript.md` | — |
| intake | LLM `/intake` | transcript.md | `idea.md` или `candidates.md` | выбор, если candidates (§3.2); ворота при confidence=low — P2-03 |
| brief | LLM `/brief` batch, диалог | idea.md + ответы | `brief.md` | всегда |
| research | код (LLM `/research` с P4-01) | — | `research.md` | — |
| prd | LLM `/prd` | brief, research, template | `prd.md` | — |
| decompose | LLM `/decompose` | prd.md | `issues.json`, `issues.md` (рисует код) | всегда |
| publish | код | issues.json | карточки Trello, `publish.json` | — |

### 3.1 ingest
- Telegram voice (`.oga`) → ffmpeg → mp3 16 kHz mono → Whisper (`whisper-1`, `verbose_json`): оттуда берутся текст, язык и длительность. `verbose_json` отдаёт только `whisper-1`, а язык прогона брать больше неоткуда.
- Демо-лимит на голосовое — 120 с. Проверяется по `duration` из самого сообщения Telegram, до скачивания и до первого потраченного цента; длиннее — вежливый отказ с предложением наговорить покороче или прислать текстом. Ограничение не Whisper, а стенда: чем длиннее идея, тем дольше думают стадии за ней. Нарезка длинного — P3-03.
- Язык Whisper называет английским словом (`russian`); в `lang` пишется код по таблице в `app/transcribe.py`. Незнакомое имя идёт дальше как есть и попадает в лог: соврать «de» вместо распознанного языка нельзя, артефакты несут его дальше.
- Пустая расшифровка (тишина, случайное нажатие) — отказ на месте, ни одна стадия не оплачивается.
- Audio file (mp3/m4a/wav): проверка `consent_confirmed`, иначе отказ с пояснением.
- Файлы > 24 МБ или > 20 мин: нарезка по тишине (ffmpeg `silencedetect`), куски ≤ 10 мин с перекрытием 5 с, транскрипция каждого, склейка по перекрытию.
- Text: без транскрипции, `duration: null`, `consent_confirmed` не пишется: записи нет.
- Голосовое `consent_confirmed` тоже не несёт: человек записывает сам себя, а § 201 StGB — про чужой разговор. Кнопка согласия приезжает вместе с файлами с диктофона (P3-02), и `source: file` появляется там же.
- Frontmatter transcript.md: `run_id`, `source`, `duration`, `lang` (Whisper language detection); `consent_confirmed` — только для аудио.
- `run_id` выдаётся здесь и больше нигде: это `runs.id` (§4), и он один на весь прогон. В боте его выдаёт запись строки `runs` при получении сообщения, в локальном прогоне без базы — `ingest` при записи `transcript.md`. Дальше он идёт по артефактам как данные, а не сочиняется заново на каждом шаге.

### 3.2 Ворота
Сообщение в Telegram с кратким содержанием артефакта + inline-кнопки: **Дальше** / **Править** / **Стоп**. «Править» — пользователь пишет текст, он попадает как `user_edit` в следующий вызов той же стадии (стадия перезапускается с правкой). Предыдущий ответ стадии при этом обязан идти в истории вызова, тем же механизмом, что и ремонтный повтор (§7): иначе стадия соберёт артефакт заново и идентификаторы issues поедут. Проверено вручную на прогоне 07.09.2026: с ответом в истории правка вышла точечной, изменился только один заголовок. Таймаут ворот — 24 ч, после этого run → `stalled`.

`auto_approve=true` (флаг run) пропускает ворота, кроме consent. Только для демо. Стадия `brief` при этом получает `interactive: false` — тот же параметр, которым пользуется локальный прогон (§7.1). Сегодня этот параметр стоит в записи стадии, а не выводится из флага: диалога нет до P2-04, и `interactive: true` собрал бы бриф из вопросов, на которые некому ответить.

Остановок у обхода два рода, и флаг снимает только один. **Ворота** — человек подтверждает готовый артефакт (после `brief` и `decompose`); подтвердить их за него флаг может. **Выбор** — человек выбирает одну идею из нескольких (`candidates.md` после intake); подтверждать там нечего, а выбрать за человека значило бы выдумать данные, поэтому `auto_approve` выбор не снимает. `candidates.md` intake отдаёт в двух разных случаях: идей несколько и идеи нет вовсе (короткое или оборванное голосовое). Сообщение бота их поэтому не считает, а просит прислать одну идею и подробнее: 08.09.2026 на двухсекундном голосовом бот отвечал «в сообщении несколько идей», тогда как в артефакте стояло «Идея не найдена». Отсюда ограничение демо: прогон со стенда встанет, если в сообщении больше одной идеи, а кнопки выбора у него нет до P3-04 — на стенде идеи присылают по одной. Ворота после intake по `confidence: low` — тоже ворота, но условные, и появляются вместе с кнопками в P2-03.

### 3.3 brief-диалог в Telegram
`/brief` в режиме batch задаёт вопросы по одному; ответы пользователя — обычные сообщения. Стадия хранит историю в `runs.brief_dialog` (JSON). «хватит» / кнопка «Собирай» завершает.

## 4. Данные

`runs`: id (он же `run_id` во всех артефактах, таблицах и маркерах Trello), chat_id, source, lang, kind, status (`ingesting|intake|awaiting_gate|brief|research|prd|decompose|awaiting_publish|published|failed|stalled`), consent_confirmed, auto_approve, created_at, updated_at.
`artifacts`: run_id, stage, path, version, created_at — каждая перезапись стадии = новая версия, старые не удаляются.
`gates`: run_id, stage, decision (`next|edit|stop`), user_edit, decided_at.
`publish_log`: run_id, issue_id, trello_card_id, url.

Файлы прогона лежат в `runs/<run_id>/` (S3-совместимо позже), `inputs/` и `outputs/` — только для локального запуска через `make run-text`.

## 5. Контракты артефактов
- `transcript.md`, `idea.md`, `candidates.md` — см. `/intake`
- `brief.md` — frontmatter `name`, `kind`, `lang`, `open_questions` — см. `/brief`
- `prd.md` — таблица «Скоп MVP» с `ID`, приоритет, `Зависит от`, критерий готовности — см. `/prd`
- `issues.json` — схема в `/decompose`; `run_id` верхнего уровня — это `runs.id` прогона (§4), пришедший от `ingest` через цепочку артефактов; `decompose` дописывает его в файл, `publish` только читает. Он отличает карточки этого прогона от чужих на общей доске. Публикация его не выдумывает: свой идентификатор означал бы, что у одного прогона их два, и воркер фазы 2 искал бы прогон по номеру, которого нет в базе. Формат маркера от этой правки не меняется, поэтому доска переживёт переход без чистки. `deferred` несёт `scope_id`, `title` (заголовок скоупа из таблицы PRD) и `reason`; дополнительно к схеме: `estimate: "S|M|L"` (S ≤ 2 ч, M ≤ полдня, L ≤ день) и `test_hint` (одна строка, как проверить) — поля взяты из практики Task Master. Инварианты, которые проверяет `app/validate.py`: фазы нумеруются с единицы, идентификаторы уникальны, каждый `phase` объявлен в `phases`, каждый `depends_on` существует, в графе нет циклов, зависимость не указывает в более позднюю фазу (иначе фаза не собирается в самостоятельный кусок работы и `/publish` не создаст под неё список)
- `publish.json` — маппинг локального идентификатора (`I-00N`, для отложенных `S<N>`) → `key`, `card_id`, `url`. Кэш: журнал целиком восстанавливается с доски по маркерам, поэтому его потеря ничего не ломает

## 6. Trello
- Одна доска на команду, `TRELLO_BOARD_ID` в .env. Ключ и токен уходят заголовком `Authorization: OAuth …`, а не в query string: URL виден прокси и попадает в тексты ошибок. По той же причине клиент не пользуется `raise_for_status`, а поднимает своё исключение со статусом, методом и путём без параметров. Публикация закрыта тем же флагом `ALLOW_LIVE_API`, что и вызовы модели: мусорные карточки на командной доске — такой же необратимый расход, как оплаченный токен.
- Списки: `Backlog`, по одному на фазу `Phase 1: <title>` … создаются при первой публикации, если нет, и каждый новый встаёт правее прежних (`pos=bottom`): без этого Trello кладёт список в начало доски, и фазы выстраиваются справа налево.
- Ключ задачи сквозной по доске: `PROJECT_KEY-N` (`PROJECT_KEY` из .env, номер без ведущих нулей). Номер выдаёт publish при создании карточки, продолжая максимальный среди маркеров с текущим `PROJECT_KEY`; ключ, не совпавший с шаблоном, и карточка без маркера номер не резервируют. `PROJECT_KEY` проверяется в `app/publish.py`, а не в `Settings`: иначе пустое значение роняло бы импорт у бота и стадий, которым Trello не нужен. Локальные `I-00N` остаются внутри прогона: их выдаёт `/decompose`, и на общей доске они сталкиваются, потому что каждый прогон начинает нумерацию заново. Сквозной ключ снимает это столкновение и даёт задаче имя, которое можно назвать вслух.
- Карточка = issue: имя `[KEY-N] <title>`, description + DoD как чеклист, label по `area`, `scope_id` в description (Trello custom fields платные — не использовать).
- Зависимости: строка «Depends on: DCT-3, DCT-7» сквозными ключами в description + attachment-ссылка на карточку. Карточки создаются в порядке зависимостей, а не в порядке файла: ссылка требует, чтобы карточка-зависимость уже существовала, а в файле зависимость может стоять ниже зависящего. Цикла не будет, его исключает §5.
- Порядок карточек в списке задаётся `pos` при создании, по порядку issue в файле, а не по порядку публикации: публикуем по зависимостям, и без этого `I-010` лёг бы выше `I-006`, что читается как сбитая нумерация. Отложенные нумеруются отдельно, внутри `Backlog`. Позиции идут от единицы, а Trello раздаёт свои десятками тысяч, поэтому опубликованная пачка садится в начало списка: на доске, где `Backlog` уже не пуст, она встанет над чужими карточками. Уже созданной карточке `pos` не выставляется и не сверяется: перетащить её руками это решение человека, а publish не арбитр.
- `deferred` из `issues.json` попадает в `Backlog` отдельными карточками: имя `[KEY-N] <title>`, причина в description, label `deferred`, чеклиста нет. Номера идут из того же счётчика, что и у issues.
- Идемпотентность: последняя строка description — маркер `dictum:<KEY-N> run:<run_id> local:<I-00N|S<N>>`. Ключ отвечает на вопрос «какой номер занят», пара `run` и `local` — на вопрос «этот issue этого прогона уже опубликован»; без `run` два прогона с одинаковыми `I-001` были бы неразличимы. Перед публикацией читаются все карточки доски, включая архивные, вместе с их чеклистами и вложениями; уже опубликованное узнаётся по маркеру. Маркер ищется терпимо к отступам и CRLF и берётся последний в описании: карточку правят руками в вебе, а текст issue может процитировать чужой маркер. `publish` — запись того же списка стадий (§7.2), поэтому бот доходит до карточек тем же обходом, что и остальные стадии; отдельная команда `python -m app.publish outputs/issues.json` остаётся для локального прогона, где публикация тратит деньги на доске и заслуживает собственного подтверждения. Истина о публикации живёт на доске; `publish.json` рядом с `issues.json` — кэш отображения, он дописывается после каждой карточки и после прогона, содержит только ключи текущего файла и не читается обратно. Таблица `publish_log` (§4) появится в фазе 2 и заменит файл.
- Карточка с маркером, у которой не хватает чеклиста DoD, его пунктов или ссылок на зависимости, дособирается: оборвавшийся прогон успевает создать карточку раньше, чем наполнить её, и без досборки она осталась бы недоделанной навсегда. Пункты сверяются по именам, недостающие дописываются в конец, поэтому после досборки их порядок может не совпадать с `issues.json`: критерии готовности не последовательность шагов, а вычислять позицию между соседями (Trello раздаёт их от 2^47) дороже, чем стоит косметика. Существующий чеклист не пересоздаётся, чтобы не терять отметки. В выводе это «уже есть, дособрана».
- Ретраи Trello (дополнение к §7, которое там не описано, потому что относится не к модели): 429 повторяется до трёх попыток с паузой из `Retry-After`, иначе 1 с с удвоением; 5xx повторяется только на GET. Каждый повтор пишет строку в лог: молчаливый повтор не отличить от его отсутствия, а знать это нужно. Повтор POST после 5xx запрещён: запрос мог дойти и потерять ответ, а вторая такая же карточка хуже упавшего прогона.
- Коды возврата `python -m app.publish`: `0` — опубликовано, `1` — `issues.json` не прошёл проверку или доска не ответила, `64` — ошибка в аргументах или файл не читается.
- Issue, у которого маркер на доске есть, а название, description, список или лейблы разошлись с `issues.json`, пропускается и помечается в выводе «уже есть, отличается». Карточка не переписывается: правка руками на доске — тоже решение человека, а publish не арбитр.

### 6.1 Известные ограничения
- **Два publish одновременно на одну доску сделают дубли.** Между чтением доски и созданием карточки есть окно, в котором второй прогон ещё не видит чужих маркеров. На MVP публикацию запускает человек из CLI, поэтому блокировки нет; она появится, когда публиковать начнёт воркер (фаза 2) и прогонов станет несколько.
- **Маркеры старого формата не читаются.** До сквозных ключей маркер был `dictum:I-001`; такие карточки publish не узнает и опубликует заново. Демо-доска по этому случаю очищена, других досок с ними нет.
- **Стёртый маркер делает карточку невидимой.** Если строку `dictum:<KEY-N> run:… local:…` убрать из описания руками, следующий publish сочтёт issue неопубликованным и создаст вторую карточку, а освободившийся номер выдаст заново. Это цена решения «истина на доске»: другого признака у нас нет.
- **Удалённая карточка возвращается под новым ключом.** publish не помнит выданных номеров помимо доски, поэтому удалённый вручную issue публикуется заново с очередным ключом, а строки `Depends on:` и вложения у соседей продолжают ссылаться на старый: их publish не переписывает.
- **Позиции карточек не чинятся после публикации.** `pos` выставляется только при создании, поэтому карточка, переставленная руками, там и останется, а перетасованный `issues.json` порядок на доске не поменяет.

## 7. Вызов LLM-стадий
`app/stages.py::run_stage(stage, inputs: dict[str, str], run_id: str, user_edit=None, history=None, params=None) -> StageResult`
- `inputs`: путь → содержимое; пути те же, что упоминают промпты (`inputs/transcript.md`, `outputs/brief.md`, `templates/prd_oneshot.md`).
- system = `.claude/commands/<stage>.md` + `templates/api_mode.md` (режим API: файлы приложены в тегах `<file path="...">`, сохранять нельзя, итоговые файлы выводятся в таких же тегах, ничего вне тегов).
- user = `<params>` (если есть) + `<file>`-блоки входов + `<user_edit>`, если есть. `history` — предыдущие ходы диалога (brief, P2-04), вставляются перед текущим сообщением.
- `params` — параметры запуска стадии (`mode`, `lang`, `interactive`): `brief` вызывается с `mode: batch` и `interactive: false`; `research` параметров не получает, пока он стадия-код, а `mode` по `kind` брифа появится вместе с P4-01. Промпты написаны для Claude Code, где стадия ведёт диалог; в режиме API диалога нет, поэтому `templates/api_mode.md` запрещает вопросы и требует помечать неясное как `[уточнить: ...]`.
- `StageResult`: `files` (путь → содержимое из `<file>`-тегов ответа), `model`, `input_tokens`, `output_tokens`, `duration_ms`.
- Набор файлов проверяется: `intake` → ровно один из `inputs/idea.md` / `outputs/candidates.md`; `decompose` → только `outputs/issues.json`; остальные стадии → ровно один свой файл. `outputs/issues.md` дописывает `app/render.py` из разобранного JSON, уже после проверок: модель писала бэклог дважды, половина выхода стадии уходила на копию, потолок токенов срезал ответ целиком, и две копии могли разойтись молча. Любой другой набор — `StageError`. Файлы на диск пишет вызывающий: CLI в `outputs/`, воркер в `runs/<run_id>/` с версиями (§4).
- Потолок ответа: `ANTHROPIC_MAX_TOKENS`, по умолчанию 24000. Клиенту задан явный таймаут в десять минут: без него SDK оценивает скорость выхода в 28 токенов в секунду и запрещает нестримовый запрос уже с 21334 токенов, тогда как стадии выдают около 110 в секунду.
- Модель: `ANTHROPIC_MODEL`, для `decompose` — `ANTHROPIC_MODEL_DECOMPOSE`. Обе по умолчанию `claude-sonnet-5`; смена дефолта — правка этой строки и `.env.example`. Из ответа берутся text-блоки.
- Каждый вызов логируется: stage, model, токены, длительность; run_id добавляет воркер (фаза 2).
- Ретраи: `max_retries=2` SDK Anthropic (сетевые ошибки, 408/409/429/5xx, экспоненциальный backoff). Ответ без единого `<file>`-тега или не прошедший проверку стадии (`decompose` → `check_issues`) → один ремонтный повтор: в диалог добавляется ответ модели и список претензий. Предыдущий ответ обязательно идёт в истории: без него стадия генерирует всё заново и идентификаторы перестают быть стабильными, чего требует `/decompose`. Если и второй ответ не проходит — `StageError` со списком проблем; локальный прогон сохраняет вторую попытку в `outputs/<stage>.raw.md` и возвращает `1`, файлы стадии на диск не пишутся. Не чинятся и дают `StageError` с полем `raw` (текст ответа) сразу: `stop_reason != end_turn`, чужой набор файлов, два блока на один путь. Это сорванный контракт, а не претензия к содержимому. Токены и длительность в `StageResult` суммируются по обоим вызовам. Содержимое файла нормализуется: ровно один перевод строки в конце. `run_id` прогона `run_stage` вписывает в `issues.json` после проверок и отказывается запускать `decompose` без него, не дойдя до вызова модели: иначе прогон оплатил бы четыре стадии, чтобы упасть на публикации.

### 7.1 Локальный прогон
`app/cli.py` (`make run-text TEXT="…"` или `--file путь`) собирает `inputs/transcript.md` из текста и гонит intake → brief → research → prd → decompose. Если у входа есть свой frontmatter, он снимается, а `lang` берётся оттуда: иначе на прогоне вышло бы два блока frontmatter и два разных языка. Приоритет языка: `--lang`, затем frontmatter входа, затем `DEFAULT_LANG`. `brief` получает `mode: batch`, `interactive: false`, `lang`. `research` — стадия-`code` (§7.2): модель не вызывается, а `outputs/research.md` пишется строкой «Ресёрч не запускался: локальный прогон через make run-text», потому что `/prd` просит этот файл на вход. Формулировку из пользовательского `skip` («по решению пользователя») здесь брать нельзя: никто ничего не решал, а артефакт уходит в `/prd` как данные. Готовый `research.md` на диске не затирается. Придёт P4-01 — запись станет `llm`, получит `inputs` и потеряет `content`; правится запись в списке, а не ветка в CLI. `--from <стадия>` (от `intake` до `decompose`) начинает прогон с указанной стадии, беря входные артефакты из `outputs/` (`inputs/idea.md` для brief): повтор упавшей стадии не оплачивает заново те, что уже прошли. Нет нужного артефакта — код `64` с именем стадии, которая его делает. Нужен и `inputs/transcript.md`: продолжается прогон, а не начинается новый, и `run_id` берётся оттуда. Транскрипта нет или в нём нет `run_id` — тоже `64`: выдать второй идентификатор значило бы, что у прогона их два, и `publish` создал бы карточки заново. `make run-text TEXT="…" ARGS=--gates` гонит прогон без `auto_approve` (рецепт пробрасывает `ARGS` в `app.cli`): обход встаёт на воротах после brief, называет артефакт и стадию, с которой продолжить (`--from research`), и отдаёт код `2`. Без флага локальный прогон авто-подтверждён, потому что нажимать в терминале некому; флаг существует, чтобы ветку с воротами можно было пройти руками до P2-03. Живой вызов API включается флагом `ALLOW_LIVE_API=true` в `.env`: без него клиент не создаётся и в сеть не уходит ничего. Флаг ставится на осознанный прогон, а не постоянно. Коды возврата: `0` — дошёл до конца, `1` — стадия упала (сырой ответ модели сохраняется в `outputs/<stage>.raw.md`), `2` — прогон ждёт человека: intake вернул кандидатов или обход встал на воротах, `64` — ошибка в аргументах запуска. Argparse по умолчанию отдаёт на такую ошибку `2`, поэтому парсер переопределён: иначе опечатка неотличима от ожидания решения.

### 7.2 Список стадий
Порядок стадий описан один раз, данными: имя, исполнитель (`llm` или `code`), входные артефакты,
выходные артефакты и параметры. Кто идёт по списку, решает сам, с какой записи начать:
CLI — от стадии в `--from`, воркер — от той, на которой стоит `runs.status`. Лесенки сравнений по
индексу в коде нет.

Список живёт в `app/pipeline.py` и знает про каждую стадию: `name`, `runs`, `inputs`, `template`,
`outputs`, `params`, `needs_lang`, `gate_after` — артефакт, который человек читает на воротах после
стадии (колонка «Ворота после» из §3 данными; `None` — ворот нет). Из `outputs` его не вывести:
после decompose читают `issues.md`, а его дорисовывает код. Данные и только данные; как по ним идти — `app/run.py`
(`walk(run, start, stop, on_done)`), общий для CLI и бота. Обратной зависимости нет: `stages` берёт
из `pipeline` контракт выходов, и обход внутри `pipeline` замкнул бы цикл.

Стадия `llm` идёт через `run_stage`. У стадии `code` в `app/run.py` есть тело — функция от прогона,
возвращающая файлы к записи: `ingest` отдаёт транскрипт с `run_id`, `research` свою строку (и пустой
словарь, если файл уже на диске), `publish` пустой словарь — карточки не артефакт прогона, а
`publish.json` он пишет сам, по карточке за раз. `outputs` у `publish` пуст по той же причине.
Язык подмешивается на ходу и только тем, у кого `needs_lang`: он свойство прогона, а не стадии. У голосового входа его называет `ingest`: `Run.lang` до расшифровки хранит язык входа (`DEFAULT_LANG` у бота), а после неё — распознанный Whisper, и `brief` получает уже его.

Обход берёт корень артефактов: локальный прогон идёт от текущего каталога (`inputs/`, `outputs/`),
бот — от `runs/<run_id>/` (§4). Обход отдаёт остановку (стадия, артефакт, род — `choice` или `gate`)
или ничего: встать он может на выборе идеи и на воротах стадии с `gate_after`, если у прогона не
стоит `auto_approve` (§3.2); на всём остальном обход доходит до конца или падает. Ворота
останавливают прогон перед следующей стадией, поэтому у последней стадии обхода они не срабатывают
(запись их объявляет, останавливать нечего): там и так конец, и «ждёт человека» вместо «дошёл до
конца» соврало бы вызывающему. Локальный прогон кончается на `decompose`, поэтому его ворота видны
только боту и тестам, идущим до `publish`.

Начать обход с середины можно, если на диске лежит всё, что обход прочитает, но сам не создаст:
`--from research` без `outputs/brief.md` отказывается с кодом `64` и называет стадию, которая этот
файл делает, а `outputs/research.md` не требует — его кладёт первая же стадия обхода. Проверка идёт
по всем стадиям обхода, а не по стартовой: иначе прогон падал бы посреди работы, успев записать
часть файлов. Раньше CLI дописывал недостающий `research.md` сам за стадию, которую его не просили
выполнять.

### 7.3 Бот демо-пути
`app/bot.py` (`make bot`) — единственный асинхронный модуль. Голосовое или текст в чат → обход
списка стадий от `ingest` до `publish` в `runs/<run_id>/` → ссылка на доску. Прогон заводится с `auto_approve=true`
(§3.2): ворота бот проходит режимом прогона, а не тем, что кнопок для них ещё нет, и включать в
P2-03 будет нечего. Само сообщение со стенда и есть подтверждение публикации.

- **Белый список обязателен.** `TELEGRAM_ALLOWED_CHAT_IDS` — id через запятую, у групп
  отрицательные. Пусто или неразбираемо — бот не стартует: имя бота публично, и каждое сообщение
  тратит ключ. Сообщение из чужого чата остаётся без ответа и попадает в лог.
- `ALLOW_LIVE_API=false` тоже останавливает старт, а не каждое сообщение по отдельности.
- Пайплайн синхронный, бот асинхронный: обход уходит в `asyncio.to_thread`, а `on_done` возвращает
  прогресс в цикл событий через `run_coroutine_threadsafe`. Одно сообщение правится после каждой
  стадии и в конце становится ссылкой. Финальная правка уходит **после** всех правок прогресса:
  те ответа Telegram не ждут, и ответ на последнюю из них, придя вторым, затирает ссылку списком
  галочек. Прогон при этом выглядит законченным, а в логе чисто — найдено живым прогоном
  0ac7bdffe0e0ba58 08.09.2026. Сбой самой правки прогресса финалу не мешает: она косметическая.
- Прогон один за раз: пока идёт первый, второе сообщение получает отказ, а не очередь. Держится
  это на двух вещах сразу: `asyncio.Lock` на прогон **и** `concurrent_updates(True)` у приложения.
  По умолчанию python-telegram-bot разбирает обновления по одному (`concurrent_updates: 1`) и
  достаёт следующее только после возврата обработчика предыдущего, то есть через весь прогон:
  замок при этом недостижим, отказа не существует, а человек молчит три минуты и потом
  оплачивает свой прогон. Найдено 08.09.2026 — три сообщения подряд дали три прогона. Состояние
  живёт в памяти процесса — до P2-02 переживать перезапуск нечему, и делать вид, что оно
  переживает, вредно.
- **Голосовое — главный вход.** `.oga` кладётся в `runs/<run_id>/inputs/`, дальше его забирает
  `ingest` (§3.1). Сообщение о ходе прогона появляется до скачивания, а не после: на чужом
  wi-fi запись едет секунды, и всё это время человек не должен смотреть в пустой чат. Первая
  строка прогресса у голосового называется «расшифровка голосового».
- Длиннее 120 с — отказ по `duration` из сообщения, до скачивания (§3.1). Голосовое не
  забралось из Telegram — отдельное сообщение с просьбой прислать ещё раз: на хотспоте это
  сеть, а не поломка прогона.
- Всё остальное (файл, документ, фото, неизвестная команда, опечатка в ней) получает короткий
  отказ с объяснением, а не молчание: молчащий бот человек у стенда читает как сломанный.
  Файлы с диктофона — P3-02.
- `ffmpeg` и `OPENAI_API_KEY` проверяются при старте, рядом с белым списком: без любого из них
  голосовое не расшифровать, а узнавать об этом на первом же сообщении со стенда поздно —
  человек увидит «прогон сорвался», хотя сломана настройка, а не прогон.
- Язык артефактов у текста — `DEFAULT_LANG` (frontmatter у него нет), у голосового — язык от
  Whisper.
- Отказы и остановки считаются по логу: `refusal=busy|too_long|unsupported|stranger` с id чата
  (у длинного голосового ещё и `seconds=`), `stop=choice|gate` с номером прогона. Отчёт
  репетиции (P2-06) отвечает на «сколько человек упёрлось» числом из `grep -c`, а не памятью;
  до 08.09.2026 ни один отказ следа не оставлял, и посчитать их было нечем.
- Обход сорвался — одно сообщение человеку с номером прогона и одна запись в лог с трассировкой.
  Отказ расшифровки — исключение из этого правила: его текст написан человеку («не разобрать
  речи», «поставьте ffmpeg») и показывается как есть, а в лог идёт строкой, а не трассировкой.

## 8. Нефункциональное
- EU-only: API-эндпоинты Anthropic/OpenAI с EU-регионом, где доступны; хостинг Hetzner.
- Аудио удаляется после успешной транскрипции, если `KEEP_AUDIO=false` (по умолчанию).
- Лимиты: ≤ 3 параллельных run на chat_id, ≤ 60 мин аудио на run. На демо-пути голосовое
  ограничено 120 с (§3.1).
- **Известное ограничение: Whisper через OpenAI — обработка вне EU.** Для демо это допустимо:
  говорит сам пользователь, о своей же идее, и запись удаляется после расшифровки. Для
  продакшена — задача фазы 3 «self-hosted Whisper на Hetzner», после неё аудио не покидает EU.
